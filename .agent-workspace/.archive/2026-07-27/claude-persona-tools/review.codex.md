# 第 1 轮评审结论

## 一、架构级问题

### A1｜工具/MCP 限制没有形成可信的安全策略闭环

- **定位锚点**：`工具限制是**收窄**语义`
- **问题**：目标承诺“工具/MCP 白黑名单”，但设计只描述 `tools`、`disallowedTools` 和具有“合并”语义的 `mcpServers`。其中 `mcpServers` 不是 MCP 白名单或黑名单；R4 提议自动补齐 ACP 工具，还可能突破用户明确选择的白名单。
- **问题根因**：把第三方 ACP 参数透传误当成完整的能力授权模型，没有定义基础权限、允许集、拒绝集、必需工具及冲突优先级。
- **业务影响**：界面可能显示子代理已受限，实际仍能使用未授权工具或 MCP；反之也可能因系统自动补齐而违反用户意图。
- **架构影响**：权限语义分散在 UI、委托参数和 ACP adapter，无法证明“最终有效权限”与用户配置一致。
- **修改建议**：
  1. 建立独立的 `CapabilityPolicy`/等价值对象，明确 baseline、allow、deny、mandatory capability 和计算后的 effective policy。
  2. 明确冲突规则，建议拒绝优先；必需工具若不在白名单，应显式提示并拒绝启动，而不是静默扩权。
  3. 将“工具限制”和“MCP server 启停/筛选”建模为两类契约，不得用 `mcpServers` 合并冒充 MCP 黑白名单。
  4. 用户显式配置限制时，若适配器不支持或忽略字段，应 fail-closed；仅未配置时才允许沿用默认 preset。
- **优先级**：**P0**

### A2｜多用户、服务器模式及权限隔离边界缺失

- **定位锚点**：`扫描 ~/.claude/agents/*.md`
- **问题**：文档直接扫描进程用户的 home 目录，但未定义桌面模式、服务器模式、多租户和远程执行主机下的“用户”分别是谁，也没有定义谁有权选择人格、修改工具限制或让 LLM 代为选择。
- **问题根因**：将单机个人环境假设直接提升为产品级目录与授权模型。
- **业务影响**：服务器模式下可能把服务账号或其他租户可见的人格暴露给当前用户；也可能扫描错误主机，导致 UI 列表与真正启动环境不一致。实际行为需实现方核实。
- **架构影响**：人格目录、租户、执行主机和会话所有者之间没有绑定关系，后续难以补足隔离而不改变接口。
- **修改建议**：
  - 定义 `principal/tenant/execution host/persona source` 四者关系。
  - 桌面模式可使用本机用户目录；服务器模式必须规定租户隔离目录或明确禁用 home 扫描。
  - 区分普通用户、管理员及 LLM 委托入口的权限；LLM 不应能绕过用户可选范围。
  - API 返回应只包含当前主体有权使用的人格。
- **优先级**：**P1**

### A3｜人格发现与校验存在两个潜在真源

- **定位锚点**：`读：list_claude_custom_agents() -> Vec<ClaudeCustomAgent>`
- **问题**：列表由 codeg 自行解析 `~/.claude/agents/*.md`，校验却要求使用 `discoverCustomAgents()`；同时文档又指出适配器读取 user/project/local 三层来源。两套发现范围与解析规则并不天然等价。
- **问题根因**：为了复用 Kiro 的 UI 形状，引入了本地扫描器，却没有确定人格目录的权威拥有者。
- **业务影响**：可能出现“UI 可见但启动时拒绝”或“适配器可用但 UI 不可见”；同名优先级和畸形 frontmatter 的处理也可能漂移。
- **架构影响**：人格目录形成双 SSOT，适配器升级后必须人工同步 codeg 解析逻辑。
- **修改建议**：
  - 优先让实际执行人格选择的 adapter/ACP 返回权威 catalog，codeg 只消费规范化结果。
  - 若受协议限制必须自行扫描，需把来源层、优先级、解析规则、内置人格过滤及版本兼容写成明确契约，并用契约测试证明与 adapter 一致。
  - catalog 项应携带来源和稳定标识，不能只靠裸名称关联。
- **优先级**：**P1**

### A4｜“无新状态机”与可续聊、可恢复目标矛盾

- **定位锚点**：`**状态机**：无新状态机`
- **问题**：目标要求派发会话可见、可续聊，但文档没有说明人格和能力策略在创建、启动失败、恢复、续聊、运行时切换及人格被删除后的生命周期。
- **问题根因**：把人格与权限视作一次性 ACP 参数，忽略它们也是需要持久化和恢复的会话启动快照。
- **业务影响**：恢复会话时可能使用不同人格或不同工具权限；人格文件被修改/删除后，旧会话行为无法预测。
- **架构影响**：`session/new`、load/resume 与 `set_config_option` 可能各自取不同配置，破坏会话一致性和审计能力。
- **修改建议**：
  - 至少定义 `SessionLaunchConfig` 快照及其生命周期，不一定需要复杂状态机。
  - 明确创建时配置、运行时配置和持久化配置的优先级。
  - 规定 load/resume 是复用原始快照、重新解析当前人格，还是要求用户重新确认。
  - 定义配置更新与会话启动并发时的原子边界，以及失败后能否安全重试。
- **优先级**：**P1**

### A5｜限界上下文与职责划分过度收缩到基础设施层

- **定位锚点**：`**Bounded context**：`acp` 基础设施层`
- **问题**：第三方 JSON 编码确实属于 ACP adapter，但人格目录、用户选择、能力策略、委托默认值、权限校验和会话快照不是纯基础设施职责。
- **问题根因**：以最终报文注入点代替业务能力边界，把“在哪里发送”误当成“谁拥有规则”。
- **业务影响**：未来新增其他 agent adapter 时，选择、校验和权限规则容易重复实现。
- **架构影响**：领域/应用规则可能侵入 `connection.rs` 和 adapter，形成贫血上层、肥大基础设施层。
- **修改建议**：
  - ACP adapter 仅负责第三方协议映射和能力支持探测。
  - 应用层负责人格 catalog、授权、配置合并、会话快照和错误映射。
  - 使用与具体 Claude JSON 解耦的 `PersonaRef`、`CapabilityPolicy`、`SessionLaunchConfig` 等值对象；不必引入重量级聚合框架。
- **优先级**：**P1**

### A6｜委托接口契约仍为悬空设计

- **定位锚点**：`工具限制需新增一个字段（见任务 4）`
- **问题**：“新增一个字段”没有字段名、类型、默认语义、序列化方式、调用方、优先级或兼容策略；“见任务 4”也没有可对应的契约定义。
- **问题根因**：注册清单和测试章节代替了正式接口设计。
- **业务影响**：UI 委托、LLM 委托和直接创建会话可能形成三套不同参数能力。
- **架构影响**：公共委托契约可能在实现阶段被临时决定，产生多处转换与兼容分支。
- **修改建议**：补齐委托输入模型、配置来源优先级、向后兼容、校验位置、错误返回和幂等语义，并明确 UI 与 LLM 是否调用同一应用服务。
- **优先级**：**P1**

## 二、普通功能问题

### F1｜用户角色和核心使用流程不完整

- **定位锚点**：`目标（一句话可验证成功态）`
- **问题**：只描述了最终能力，没有区分直接创建、从已有会话委托、LLM 自动委托、恢复会话等场景，也没有说明谁配置人格和限制。
- **问题根因**：以技术注入链路代替产品需求和用户旅程。
- **业务影响**：UI、API 和委托工具可能对“默认值、谁可修改、何时生效”作出不同理解。
- **架构影响**：需求无法映射到统一用例边界，验收覆盖也会遗漏主要入口。
- **修改建议**：补充最小角色与流程矩阵：角色、入口、选择权限、生效时点、成功结果和失败反馈；至少覆盖桌面用户、服务器用户和 LLM 委托。
- **优先级**：**P1**

### F2｜失败降级语义与“限制必须有效”互相冲突

- **定位锚点**：`**降级**：`_meta` 被适配器忽略时不得导致启动失败`
- **问题**：对显式人格选择或工具限制采用 best-effort，意味着配置被忽略后会继续以默认人格或更宽权限运行，与“不静默降级”和“收窄语义”冲突。
- **问题根因**：没有区分可选元数据和安全/身份承诺。
- **业务影响**：用户看到配置已接受，但真正会话可能未应用配置。
- **架构影响**：调用方无法根据结果判断会话是否满足启动前置条件。
- **修改建议**：
  - 未配置时可兼容旧 adapter。
  - 显式配置人格或限制时，必须确认 adapter 支持并返回 effective config；无法确认则拒绝启动并返回稳定错误。
  - 补充冲突名单、非法工具标识、畸形人格、adapter 不支持、配置过期等错误。
- **优先级**：**P1**

### F3｜验收标准未覆盖目标中的关键可观察结果

- **定位锚点**：`先写、必须先红：`
- **问题**：测试主要验证 JSON 字段和目录解析，没有验证“会话可见、可续聊”、拒绝的工具确实不可调用、MCP 限制实际生效、桌面/Web 双模式一致。
- **问题根因**：验收围绕实现结构，而不是围绕一句话成功态和安全承诺。
- **业务影响**：单元测试全绿仍可能交付一个不可续聊或限制失效的功能。
- **架构影响**：无法验证 UI—应用服务—ACP—恢复链路的端到端契约。
- **修改建议**：建立需求到验收的追踪矩阵，至少增加：
  1. 选定人格后实际会话确认有效人格；
  2. 被拒工具调用失败且原因正确；
  3. MCP 允许/拒绝策略的真实行为；
  4. 会话出现在列表并能恢复续聊；
  5. 桌面与 Web/服务器模式一致；
  6. 显式限制被 adapter 忽略时启动失败。
- **优先级**：**P1**

### F4｜关键可行性未验项缺少明确的决策出口

- **定位锚点**：`R1 + R2 必须在写实现前用一次真实 session 实测`
- **问题**：R1、R2 被列为实施前门禁，但没有定义实测通过条件、失败后的替代方案和是否需要回退设计；R3、R4 也没有最终决策责任人与截止点。
- **问题根因**：风险被记录，却未转化为可判定的架构门禁。
- **业务影响**：实测不符合假设时，开发可能继续沿原方案局部修补。
- **架构影响**：当前卡片无法作为可执行的 go/no-go 决策依据。
- **修改建议**：为每个风险写明验证输入、通过判据、失败分支和对决策卡的回写要求；R1 或能力限制不可可靠生效时，应停止实现并重新选择集成路径。
- **优先级**：**P1**

### F5｜文档存在可定位的悬空引用和编号瑕疵

- **定位锚点**：`2 工具限制是**收窄**语义`
- **问题**：不变量编号缺少 `2.`；`见任务 4` 无明确目标；测试项引用 `§5.4`，但当前文档没有对应的小节。
- **问题根因**：章节调整后交叉引用未同步。
- **业务影响**：实现者难以确认真正约束来源。
- **架构影响**：无直接架构影响，但会削弱决策卡的可执行性。
- **修改建议**：统一编号并清理所有悬空引用。
- **优先级**：**P2**
