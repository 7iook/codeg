# 第 1 轮评审结论

评审范围仅限 `design.md`、`requirements.md` 的文档内证据；其中引用的源码事实、侦察报告与 UI 设计卡均未跨目录核验。

## 一、架构级问题

### A1 · 内部 SUB 与已完成任务可能没有任何常驻入口

- **问题**：观察面板包含委托子智能体和内部 SUB，但常驻条只在“存在未完成的委托子智能体”时显示，计数也只取委托池。仅有内部 SUB、或委托全部完成后，面板入口会消失，与“永不消失”“随时打开面板”及保留已完成分区矛盾。
- **问题根因**：把入口可见性、入口计数口径、面板观察对象三件事绑定成了一个委托池条件。
- **业务影响**：用户截图对应的内部 SUB 场景可能仍需滚动消息流；委托完成后也无法重新查看已完成记录。
- **架构影响**：UI 入口与面板领域集合不一致，形成不可达状态。
- **修改建议**：重新定义入口生命周期与计数契约。入口至少应覆盖内部 SUB-only、仅有已完成记录及空态访问场景；若计数仍只显示委托池，必须另有不依赖委托运行态的固定入口，并明确总数、运行数和来源口径。该能力属于 **A 业务刚需**。
- **优先级**：**P0**
- **定位锚点**：`### Requirement 5: 常驻入口`

### A2 · 四分区把会话归属与生命周期混成互斥枚举

- **问题**：“当前会话 / 其他会话 / 已完成 / 未归属”并不天然互斥。一个已完成任务仍可能属于当前会话、其他会话或未归属；Property 1 却要求每行恰好进入其中一个分区。
- **问题根因**：将两个正交维度——`conversation scope` 与 `lifecycle status`——压进一个单值分区字段，且没有定义优先级。
- **业务影响**：同一任务在不同实现者手中可能被放进不同分区，用户无法形成稳定心智模型。
- **架构影响**：selector、排序、计数和属性测试都没有唯一正确结果。
- **修改建议**：将“会话归属”和“生命周期”建模为独立维度，再明确 UI 如何投影；若坚持单层四分区，必须定义完整优先级及每种交叉组合的归类规则，并同步 Requirement 4/6、Data Models 和 Property 1。
- **优先级**：**P0**
- **定位锚点**：`### Property 1: 分区划分的完备与互斥`

### A3 · 内部 SUB 没有可判定的生命周期，却被要求展示运行态和已完成态

- **问题**：设计仅写“由是否仍在来帧推断”内部 SUB 状态，没有终止事件、静默阈值、宿主 turn 结束规则或重连后的恢复规则。
- **问题根因**：把“近期活动证据”误当成了“权威生命周期状态”。没有新帧既可能表示完成，也可能表示思考、阻塞或网络中断。
- **业务影响**：运行中的 SUB 可能被提前归为完成；已结束的 SUB 也可能长期显示运行中，用户无法判断是否需要干预。
- **架构影响**：运行计数、已完成分区、排序和验收条件均无法确定性实现。
- **修改建议**：指定权威结束信号及状态机；若当前事件源确实不提供终态，应把内部 SUB 降级为“活跃度未知/最近活动”，不得承诺准确的运行或完成状态，并调整分区和文案。相关事件能力需实现方核实。
- **优先级**：**P0**
- **定位锚点**：`由是否仍在来帧推断`

### A4 · 委托任务缺少归入“当前/其他会话”所需的数据链

- **问题**：文档列出的 `DelegationBinding` 字段没有 `parentConversationId`，Data Models 却以“`childConversationId` 的父会话”作为归属来源，未说明谁查询、何时查询、失败如何处理。
- **问题根因**：selector 的输出契约依赖一个未纳入输入契约的字段。
- **业务影响**：委托任务可能被误归当前会话、全部落入其他会话，或无法展示。
- **架构影响**：`Context → selector → UI` 的单向链路缺了一跳；所谓纯 selector 无法只靠声明的输入完成分区。
- **修改建议**：补齐 parent conversation 的权威来源、解析责任层、缓存/失效和失败语义；若 Provider 本身按会话隔离，也需明确说明并限制“其他会话”能力。现有映射能力是否存在需实现方核实。
- **优先级**：**P0**
- **定位锚点**：`会话归属 | \`binding.childConversationId\` 的父会话`

### A5 · “归属校验”没有绑定调用者身份，无法证明租户隔离

- **问题**：用户侧根据目标 `child_conversation_id` 解析出该目标自己的 `parent_conversation_id`，再用它与 broker 中任务记录比较。文档没有任何 authenticated principal、账户或租户参与校验。
- **问题根因**：将“目标数据内部自洽”当成“调用方拥有目标”。二者不是同一个安全命题。
- **业务影响**：若服务器允许多账户或多租户，知道其他子会话 ID 的用户可能取消不属于自己的任务。
- **架构影响**：API、数据库查询与 broker 边界缺少统一授权主体；`unknown_report` 只能隐藏结果，不能补足授权。
- **修改建议**：先明确产品是单用户信任域还是多租户服务。单用户模式应写明边界和不支持项；多租户模式必须从认证层传入主体，并在解析目标时校验账户/租户归属，而不是把目标自身父会话当调用者凭据。具体部署认证现状需实现方核实。
- **优先级**：**P0**
- **定位锚点**：`### Requirement 8: 用户侧取消的传输通道`

### A6 · 核心载体与消息详情链路尚未决策，设计不可直接实施

- **问题**：D5 仍为 `unverified`，Popover、Sheet 及组合方式没有定稿；同时 Requirement 6 要求“就地展示消息内容”，但委托行的数据源仅包含绑定元数据，没有定义委托消息的加载接口、选中态或失败态。
- **问题根因**：在关键交互和消费链路尚未闭合时，提前固化了组件、selector 和验收要求。
- **业务影响**：实现后可能只能看到摘要，无法满足“查看某个子智能体的消息”的核心诉求，或被迫中途改造载体。
- **架构影响**：最终 sink、数据获取方式和组件边界不确定，无法评估性能、错误处理及复用范围。
- **修改建议**：先定稿载体和交互；分别给出委托子会话与内部 SUB 的消息来源、加载粒度、选中状态、加载/空/错误态以及 Open in Tab 的关系，再冻结任务拆分。
- **优先级**：**P0**
- **定位锚点**：`### D5 · 清单载体（待 UI 设计卡返回后定稿）`

## 二、普通功能与生产边界问题

### A7 · “保留到会话关闭”的生命周期和容量边界不明确

- **问题**：文档把完成记录绑定到 Provider 生命周期，却没有定义“会话关闭”是关闭 tab、切换会话、Provider 卸载、刷新页面还是断线重连；委托完成记录也没有数量上限。
- **问题根因**：以实现对象生命周期替代业务生命周期，没有说明多 tab、刷新和长期会话下的行为。
- **业务影响**：记录可能过早丢失，也可能在长会话中无限积累；不同部署模式体验不一致。
- **架构影响**：内存、恢复语义和多会话隔离不可预测。
- **修改建议**：定义业务生命周期事件、刷新/重连策略、多 tab 行为、委托记录上限和淘汰可见性；明确 Provider 是否按会话隔离。
- **优先级**：**P1**
- **定位锚点**：`### D3 · 已完成态由前端自留，不新增后端持久化`

### A8 · 新能力缺少逐项业务现实分类，部分要求疑似 Solution-Jumping

- **问题**：spec 没有对新增只读投影、稳定引用、selector、常驻条、清单载体、上下文菜单、取消通道等逐项给出 A/B/C/D 分类。“投影引用稳定以便 memo 命中”尤其只有技术理由，没有用户损失或性能证据。
- **问题根因**：把实现便利和现有代码缺口直接提升为需求。
- **业务影响**：可能为用户不可感知的能力增加维护面，同时遗漏真正关键的入口和生命周期问题。
- **架构影响**：业务需求、稳定性保护与实现细节混在同一需求层，难以裁剪和验收。
- **修改建议**：在需求入口处增加能力分类与追踪：用户场景、缺失影响、现有覆盖、A/B/C/D。纯技术支撑项应追踪到上层业务 AC；无法说明真实影响的稳定引用等要求应删除或降为实现建议。
- **优先级**：**P1**
- **定位锚点**：`## Requirements`

### F1 · 淘汰条目后要求 UI 解释，但没有保留任何可观察信号

- **问题**：Provider 按插入序删除最旧内部 SUB 后，UI 被要求“显示说明文本、不静默消失”，但设计没有 tombstone、淘汰计数或事件。
- **问题根因**：生产者删除了消费者生成说明所需的唯一证据。
- **业务影响**：列表项目会无提示消失，用户可能误以为任务结束或数据损坏。
- **架构影响**：Error Handling 的要求无法由已声明接口实现。
- **修改建议**：增加最小的淘汰可观察结果，例如聚合计数或一次性事件；若不值得增加状态，则删除“逐项说明”的承诺，改为面板级容量提示。
- **优先级**：**P1**
- **定位锚点**：`| 内部 SUB 超 64 条被淘汰 | UI |`

### F2 · 取消操作缺少并发、重复请求和完成竞态契约

- **问题**：仅定义单次取消成功/失败，没有覆盖双击、两个客户端同时取消、取消与自然完成交错、响应乱序及断线后重试。
- **问题根因**：把取消视作瞬时 UI 动作，没有定义其幂等语义和状态迁移。
- **业务影响**：用户可能看到失败后实际已取消、重复错误提示，或终态被较晚响应覆盖。
- **架构影响**：前端临时状态与 broker 终态可能出现双真源。
- **修改建议**：明确重复取消和“已完成”结果是否视为幂等成功，规定竞态时终态优先级、按钮禁用范围、响应乱序处理及重连后的权威状态重取方式。
- **优先级**：**P1**
- **定位锚点**：`### Requirement 7: 行操作`

### F3 · 新取消 API 的对外契约不完整，且与“wire 零改动”表述冲突

- **问题**：设计只给出 HTTP 方法、路径和 camelCase，未定义请求/响应 JSON、HTTP 状态、认证上下文、超时、错误映射、审计字段；同时声称“wire 契约零改动”，但新增 HTTP/Tauri 接口本身就是外部传输契约变化。
- **问题根因**：把事件 wire 与命令/API wire 混为一谈，并用既有报告类型替代完整接口契约。
- **业务影响**：桌面和服务器模式可能产生不一致的错误体验，调用方难以稳定处理失败。
- **架构影响**：Transport、防腐层和可观测性边界不明确。
- **修改建议**：限定“零改动”仅指既有事件/快照 wire；补齐取消接口的输入输出、状态码、稳定错误、认证授权、timeout、request_id/审计日志及两种运行模式的一致性验收。
- **优先级**：**P1**
- **定位锚点**：`wire 契约零改动。`

### F4 · 核心验收仍存在不可量化和口径未定义

- **问题**：Success State 使用“数秒内”，没有确定上限；“消息内容”未说明是完整 transcript、tail 还是摘要；“未完成”对内部 SUB 没有定义；取消失败状态保留多久也不明确。
- **问题根因**：验收描述混入用户感受，但没有转成可测量的业务后置条件。
- **业务影响**：实现方和验收方可能在性能、消息完整性及状态展示上产生争议。
- **架构影响**：端到端测试无法形成稳定断言，可观测指标也无法据此建立。
- **修改建议**：定义取消响应与实际 teardown 的时间边界、消息详情最小内容与加载范围、各来源的“未完成”判据，以及失败提示的清除/重试规则。
- **优先级**：**P1**
- **定位锚点**：`## Success State (§0.16 · MANDATORY · sourced, NEVER self-invented)`
