# 第 3 轮评审结论

评审范围仅限 `design.md`、`requirements.md`、`review.codex.md`、`review2.codex.md`。文档中的源码事实、侦察结论和 Git 史料均未核验，以下涉及实际结构的判断均以 spec 自述为前提。

## 真实业务边界清单

### 典型场景

- 单用户在一个会话内同时运行多个委托子智能体，可查看、跳转、取消。
- 同一会话同时存在委托子智能体与 Claude 内部 SUB；两者展示统一，但操作能力不同。
- 委托自然完成、失败或被取消后，记录在当前工作区存续期内供用户回看。
- 用户选中委托行时按需读取一条摘要；切换选中项时旧请求结果不得污染新行。

### 复杂场景

- 多会话、多 tab 并行运行时，当前会话、其他会话、未归属和终态条目必须保持可追溯关系。
- `delegation_started` 可能来自实时事件，也可能由重连后的活动任务快照回放；两条路径必须生成同构的 `parentConversationId`。
- `session_id → conversation_id` 映射可能晚于内部 SUB 帧到达，必须在映射更新后重新归属。
- 取消请求、自然完成事件、HTTP 响应、断线和重连可能乱序到达。
- 前后端混合版本运行时，新增 `BackgroundActivity` 分类字段可能缺失，需有明确退化显示。

### 极端场景

- 内部 SUB 超过 64 条、委托 binding 长时间累计、多个会话同时触发淘汰。
- 用户在取消请求超时后重试，但第一次请求实际上已在服务端成功执行。
- broker 已完成取消，但完成事件在断线期间丢失；重连快照又只包含运行中任务。
- 当前会话没有任何条目，但其他会话仍有运行任务；用户仍需要进入全局观察清单。
- 多名操作者共享同一个服务器 token 时，任一操作者可能取消另一操作者的任务。

### 与本领域无直接关系的边界

- 店铺、平台、业务账户和外部业务数据源不属于当前 agent-runtime 领域，不应为其预建抽象。
- “多租户”在本 spec 中表现为多操作者或多个隔离工作区，而非电商租户模型；是否属于支持的生产拓扑必须由产品负责人确认。
- 本期没有传统历史业务数据迁移，但存在**活动任务快照兼容迁移**和新增事件字段的版本兼容问题。

## 当前方案继续实施的风险

### C1 · 实时事件与重连快照没有形成统一的会话归属契约

- **定位锚点**：`THE DelegationBroker SHALL 在 delegation_started 事件中携带该委托的 parent_conversation_id。`
- **层次**：架构级。
- **问题**：Requirements 只要求实时 `delegation_started` 带 `parent_conversation_id`，但 design 明确活动委托还会由快照 seed 回放，同时又声明 `ActiveDelegationState` 沿用不改。文档没有说明重连快照如何取得同一字段。design 内部还残留三种互斥说法：
  - Architecture 写内部 SUB 在 Provider 内解析归属；
  - Requirements 写 selector 基于映射快照解析；
  - Data Models 仍写委托通过 `parentConnectionId` 判归属。
- **问题根因**：R2 修改了实时 selector 契约，但没有同步所有 producer、回放路径和设计章节。
- **业务影响**：实时运行正常，服务重连或快照恢复后，同一个运行任务可能突然进入未归属或其他会话。
- **架构影响**：实时事件与快照形成两种 `DelegationBinding` 形状；实现方会按不同章节实现不同真源。
- **修改建议**：定义唯一 canonical record，明确实时事件、活动快照、seed 回放都必须产生同构的 `parentConversationId`；同步清理 Provider 解析和 `parentConnectionId` 的旧描述。快照是否已有可用字段，**需实现方核实**。
- **优先级**：**P0**

### C2 · 多会话观察入口与分区模型仍无法共同成立

- **定位锚点**：`WHILE 当前会话的观察集合非空, THE 子智能体常驻条 SHALL 保持可见。`
- **层次**：架构级。
- **问题**：面板承诺展示“其他会话”折叠段，但入口只在当前会话集合非空时出现。当前会话为空、其他会话仍在运行时，其他会话清单不可达。design D3 又称“面板只展示归属为当前会话的条目”，与 Requirement 6.2 直接冲突。终态条目一律进入单一“已完成”区后，其会话归属如何展示、如何执行“每会话上限”也未定义。
- **问题根因**：把会话局部入口、工作区级 Provider 和跨会话观察能力混成一个生命周期。
- **业务影响**：多会话并行时，用户可能完全看不到仍在其他会话运行的任务；完成记录也可能跨会话混杂。
- **架构影响**：入口可见性、selector 输出、分区和容量裁剪没有统一作用域。
- **修改建议**：明确二选一：
  1. 本期是当前会话面板：删除其他会话分区；
  2. 本期是工作区观察面板：只要工作区观察集合非空就保留入口，并让所有终态记录继续携带、展示会话归属。  
  按已写明的产品范围，推荐第二种。
- **优先级**：**P0**

### C3 · “运行中→已静默”只有时钟入参，没有生产调度者，且常驻条计数出现零值悖论

- **定位锚点**：`WHILE 一个内部 SUB 自最后一帧起未超过静默判定阈值`
- **层次**：普通功能缺陷。
- **问题**：`now` 显式入参只解决了纯函数测试问题，未定义无新帧时由谁、按什么频率触发 selector 重算。若页面没有其他渲染，内部 SUB 永远不会转为已静默。此外，R5.4 在“没有运行中条目”时显示“已完成数”，但内部 SUB 的已静默状态明确不是完成；仅有静默 SUB 时会出现入口可见但数字为 0。
- **问题根因**：活动证据模型与入口计数仍沿用委托终态模型。
- **业务影响**：状态长时间不刷新，或面板明明有条目却显示 0。
- **架构影响**：selector 契约完整，但调用方生命周期契约不完整。
- **修改建议**：指定唯一轻量调度者及刷新频率，并在面板关闭或无内部 SUB 时停表；常驻条无运行中条目时应显示“可观察条目数”或分别表达静默与终态数量，不得把静默计为完成。
- **优先级**：**P1**

### C4 · 事件流作为唯一终态真源时，没有处理事件丢失和重连恢复

- **定位锚点**：`THE 观察面板 SHALL 以 delegation_completed 与 delegation_session_update 事件流作为委托行生命周期的唯一真源。`
- **层次**：架构级稳定性问题。
- **问题**：取消响应不得更新生命周期是合理的，但若服务端已取消、终态事件在断线期间丢失，前端会清除在途标记并继续显示运行中。重连快照又只包含运行任务，无法为旧行提供取消终态。
- **问题根因**：文档把“单一真源”等同于“单一瞬时推送通道”，没有给至少一次交付或状态对账机制。
- **业务影响**：取消真实成功但 UI 长期显示仍在运行；用户重复取消并收到不易解释的终态报告。
- **架构影响**：实时投影无法从网络中断恢复到 broker 权威状态。
- **修改建议**：不要引入复杂事件溯源；采用最小恢复路径即可：取消获得终态报告后触发一次权威状态刷新，或重连时用包含终态/版本的快照对账。明确重复取消、请求超时后重试和旧响应晚到的结果。
- **优先级**：**P1**

### C5 · 容量策略的作用域和数值仍未达到开工标准

- **定位锚点**：`| **本轮新增** | 前端**委托绑定元数据**`
- **层次**：普通生产准备缺陷。
- **问题**：委托 binding 上限仍为“待定”，已完成区“每会话显示上限”也没有数值或配置来源。内部 SUB 淘汰计数写“自会话开始以来”，但 Provider 又是工作区级，计数何时重置不明确。
- **问题根因**：识别了容量风险，但没有用生产规模和生命周期定义完成参数化。
- **业务影响**：实现者只能自行猜常量；过小会误删可见记录，过大仍可能造成长时间内存增长。
- **架构影响**：Provider 容量、UI 裁剪和提示计数的作用域不一致。
- **修改建议**：开工前取得典型及极端并发基线，确定两个常量和重置作用域；不必新增设置页。淘汰提示至少区分内部 SUB 与委托终态，避免把全工作区累计量解释成当前会话数据。
- **优先级**：**P1**

### C6 · 取消接口的生产信任边界仍是条件性前提

- **定位锚点**：`THE 取消 HTTP 路由 SHALL 与既有 delegation 路由使用同一认证中间件。`
- **层次**：安全边界。
- **问题**：spec 已诚实记录全局 token 无 principal，但尚未把“仅单一可信操作者”写成部署支持边界或上线门禁。
- **问题根因**：以当前实现没有租户模型，推导生产环境不会由多名操作者共享。
- **业务影响**：若服务器模式允许团队共享 token，任一操作者都可能查看或取消其他操作者的委托。
- **架构影响**：一旦未来补多租户，四条 delegation 用户通道都需整体迁移，不能只修取消接口。
- **修改建议**：本期不应夹带 principal 重构；但必须由产品确认服务器模式是否只支持单一信任域，并在部署边界中明确。若支持多操作者，本 spec 应暂停取消接口上线并拆出统一授权改造。
- **优先级**：**P1，若确认支持多租户则升级 P0**

## 推荐的更优实现方向

推荐保留当前总体方向，但在开工前收敛为四条更简单的生产契约：

1. **统一 producer 契约**  
   实时事件、活动快照、seed 回放统一产出同一种委托记录，至少包含稳定任务标识、`parentConversationId`、状态和能力。

2. **明确工作区级观察作用域**  
   Provider 既然位于工作区级，入口和清单也按工作区观察模型设计；当前会话仅作为默认排序和展开优先级，不作为入口存在条件。

3. **活动证据与终态分开计数**  
   委托使用权威生命周期；内部 SUB 只使用近期活动/静默。常驻条不要用一个“已完成数”同时概括静默与终态。

4. **使用最小状态对账，不建设新任务中心**  
   取消继续复用现有 broker 和事件流，但为断线、超时补一次状态刷新或重连对账。无需引入事件溯源、全局 Work Item 平台或新的持久化表。

### 本期必须实现

- 委托实时与快照回放的统一归属字段。
- 工作区级入口与跨会话可达性。
- 取消链路及事件丢失后的最小对账。
- 内部 SUB 映射迟到重算、静默调度。
- 明确容量常量、淘汰顺序和计数作用域。
- 单用户信任域上线门禁。

### 可延后

- 刷新后恢复已完成历史。
- 用户可配置的容量和静默阈值。
- 将观察面板升级为 AuxPanel 或独立任务中心。
- 多租户 principal 改造——前提是当前明确不支持多操作者共享。

### 不建议实现

- 店铺、平台、商业账户等当前领域不存在的抽象。
- 为未来载体切换建设额外容器框架。
- 为保证所有任务池数字相等而统一身份和生命周期。
- 仅因接口“看起来应成对”新增查询、限流或持久化接口。

## 开工前代码核验清单

### 当前领域模型和数据库结构

- `ActiveDelegationState` 是否已经包含或可无歧义取得 `parent_conversation_id`？
- 活动委托快照是否能为每个条目保留该字段？
- `DelegationBinding` 是否有稳定的终态到达时间，可用于确定性淘汰？
- 子会话记录与父会话的映射是否恒为一对一，是否存在被移动、删除或孤儿记录？

### 现有接口、任务和事件链路

- 实时 `delegation_started` 与快照 seed 是否经过同一个规范化入口？
- `delegation_completed` 和 `delegation_session_update` 是否覆盖所有取消路径及所有 turn version？
- WebSocket 断线期间的终态事件是否会补发，还是会永久丢失？
- 重连快照是否只包含运行态，是否存在可复用的终态对账接口？
- `getFolderConversation` 是否支持当前会话模式及服务器模式，是否会读取完整大对象？

### 数据来源及字段完整性

- `SessionState.conversation_id` 是否在委托创建时始终非空且稳定？
- `session_id` 是否在所有 `claude_subagent_message` 事件中存在？
- `session_id` 在多个工作区、连接或重启周期内是否全局唯一？
- `parent_tool_use_id` 是否可能跨会话重复？
- `taskId` 与 `parentToolUseId` 是否可能碰撞，行标识是否需要来源前缀？

### 账户、租户和实体映射

- 服务器模式是否只支持一个可信操作者？
- 多个用户是否可能共享同一 `CODEG_TOKEN`？
- 一个连接是否可能承载多个会话，或在会话间复用？
- 工作区之间的 Provider、事件广播和会话映射是否完全隔离？

### 状态机、幂等和失败恢复

- 对同一任务重复调用取消是否稳定返回同一终态？
- HTTP 超时后重试是否可能执行两次 teardown？
- 自然完成与取消同时发生时，broker 最终状态由哪一个原子操作决定？
- 旧的取消响应是否可能清除新一轮取消的在途标记？
- 服务重启后，前端残留 running 行如何与 broker 状态重新对账？
- 终态事件是否带可比较的 turn/version 信息？

### 历史 Git、旧实现和废弃逻辑

- `parent_conversation_id` 是否曾在事件或快照中存在后被删除？
- `USER_ENTRY_CONNECTION_ID` 的历史约束是否明确禁止用于真实连接解析？
- 是否已有断线重连后的 delegation 状态对账实现？
- 是否存在废弃的全量 delegation 列表或取消端点可复用？

### 前后端重复能力

- 前端是否已有工作区级活动入口，可在当前会话为空时继续访问？
- 是否已有统一的 interval/ticker 可驱动静默状态更新？
- 是否已有请求序号或 abort 机制处理摘要请求乱序？
- 是否已有容量提示、淘汰计数或 capped-map helper？
