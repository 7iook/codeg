# 第 2 轮评审结论

本轮仅依据 `requirements.md`、`design.md`、`tasks.md` 与上一轮评审反向验证，不对文档中的源码事实背书；相关实现能力仍需实现方核实。

## 一、架构级问题

### A1. 客户端 `message_id` 无法兑现“不丢且不重”的投递契约

- **定位锚点**：`design.md` → `### 2.5.1 队列项状态机（补评审 A3：证明不丢不重且可恢复）`
- **问题**：设计规定传输错误后回到 `queued` 并允许重试，同时宣称同一 `message_id` 可去重；但 `_session/steering` 参数只有 `sessionId` 与 `prompt`，没有把幂等键交给真正执行消息的 agent。若 agent 已接受请求、仅响应在网络中丢失，本地会误判失败并重发，造成重复执行。
- **问题根因**：把客户端投递标识误当成端到端幂等键；前端只能去重本地操作，不能消除远端“已执行但确认未知”的不确定窗口。
- **业务影响**：重复派发、重复修改或重复外部写操作；反之若禁止重试，又无法满足“不丢”。
- **架构影响**：文档承诺了当前协议无法证明的 exactly-once 语义，状态机的 `failed → queued` 在模糊失败下不成立。
- **修改建议**：必须二选一：
  1. 局部路径：区分“明确拒绝”和“投递结果未知”；仅明确拒绝回队，未知态不得自动重发，由用户确认或会话证据消歧，并相应收缩 R1.6；
  2. 领域路径：推动 agent 接受并持久去重 `message_id`，再声明可安全重试。
  
  在二者确定前暂停实现 T2–T6。不能用前端 `delivered` 集合假装获得远端幂等。
- **业务分类**：**B 稳定性保护**。
- **优先级**：**P0**

### A2. 取消确认允许实际终止集合扩大，破坏性操作超出用户确认范围

- **定位锚点**：`design.md` → `## 4. R4 破坏性告知设计`
- **问题**：设计承认确认框停留期间可能新增委托，却规定确认后不校验数量变化，并按确认时的当前父轮范围全部取消。若展示 3 个、确认时变为 5 个，用户实际批准的破坏范围被扩大。
- **问题根因**：把“用户想停止父轮”直接等同于“用户同意终止确认后新增的任意子任务”，没有区分集合缩小与集合扩大的风险差异。
- **业务影响**：用户可能误杀未被确认框告知的新委托及其工作成果。
- **架构影响**：只读预览与破坏性提交仍不是一致的 prepare/commit 契约；“共用作用域函数”只能保证算法一致，不能解决时序授权。
- **修改建议**：集合缩小时可继续并按实际数反馈；集合扩大时应重新确认，或让后端生成带目标集合/版本的取消预览令牌并按该令牌提交。若产品语义坚持“确认的是整个父轮而非 N 个委托”，确认文案必须明确作用域，数量只能标为动态估计，AC4 也不能再要求数量等同授权边界。
- **业务分类**：**B 稳定性保护**。
- **优先级**：**P0**

### A3. `startedNewTurn` 用本地布尔值和超时模拟权威 turn 生命周期

- **定位锚点**：`design.md` → `### 2.4 startedNewTurn 竞态处理`
- **问题**：文档已承认客户端拿不到新 turn 的终态，却仍计划设置 `turn_in_flight = true`，再由“任一终态事件或超时”恢复 idle。无法证明该终态属于 detached turn；超时发生时远端也可能仍在执行。
- **问题根因**：用启发式状态修补上游缺失的 turn identity/lifecycle 契约。
- **业务影响**：过早恢复 idle 会放行新的普通 prompt 并触发忙碌错误；错误消费其他终态会使 UI 与真实执行状态漂移。
- **架构影响**：本地 `turn_in_flight` 不再是事实，而成为猜测；后续 flush、取消与发送决策都会继承污染。
- **修改建议**：不要把该结果映射成普通 `turn_in_flight`。定义独立的“已接受但生命周期不可观测”状态，期间阻止依赖 idle 的自动 flush；只能通过可关联的 turn 事件、明确状态查询或重连快照收敛。若没有可靠恢复信号，应将 `startedNewTurn` 标为协议限制并关闭该竞态路径，而不是用超时伪造终态。
- **优先级**：**P1**

### A4. “成功后写会话记录”隐含了响应一定先于流事件到达

- **定位锚点**：`design.md` → `### 2.6 注入消息的会话记录真源（补评审 F2 · R1.5）`
- **问题**：设计在收到 outcome 后才写用户消息，却断言记录会按实际投递时刻排列。文档没有证明 steering 响应必定先于对应 agent 流事件被消费。
- **问题根因**：把 RPC 确认顺序当成会话事件顺序，未定义记录与流事件的串行化边界。
- **业务影响**：可能先显示 agent 回答、后出现触发它的用户消息；刷新后的 transcript 顺序也可能失真。
- **架构影响**：广播、transcript 与 agent update 三条时序缺少统一提交点。
- **修改建议**：明确 outcome 与 update 的时序保证；若不能保证，应在后端创建不可见或 pending 的记录占位，明确失败回滚/失败态，再按 `message_id` 提交，或在释放关联流事件前完成记录。具体既有事件管线能力需实现方核实。
- **优先级**：**P1**

## 二、需求与任务问题

### F1. R6 仍未完成业务裁决，却继续占用设计和交付范围

- **定位锚点**：`requirements.md` → `### R6 resume 用户入口`
- **问题**：文档没有回答具体角色、操作、损失与现有覆盖，设计仍写“若缺，补前端入口”，任务也继续预留实现分支。
- **问题根因**：把是否存在 UI 入口这个技术调查结果，当成决定是否开发的条件。
- **业务影响**：核心 steering 交付可能被一个尚无用户损失证据的独立功能拖慢。
- **架构影响**：会话恢复领域被继续混入 turn steering 与委托取消领域。
- **修改建议**：当前证据下直接裁决为 **D 技术缺口**，停止开发并移出本 spec；以后若出现明确恢复失败场景，再单独立项。仅保留“已评估、不实施”的决策记录。
- **优先级**：**P1**

### F2. Tasks 中的 Steer 命令契约与设计不一致

- **定位锚点**：`tasks.md` → ``ConnectionCommand::Steer { blocks, mode }``
- **问题**：设计定义 `Steer { blocks, message_id, reply }`，任务却写成 `{ blocks, mode }`；而当前方案已经明确没有发送模式，且 outcome 必须通过 oneshot 返回。
- **问题根因**：R1 修订后任务清单未同步，残留了废弃的 mode 模型。
- **业务影响**：executor 按 tasks 实现会缺失结果回传或消息关联，直接破坏失败回队、记录去重与 AC1.1。
- **架构影响**：设计与执行契约出现两个真源。
- **修改建议**：统一命令字段、返回方式及所有权；同时检查 T2、T3、T6 对同一 `message_id/outcome` 契约的引用一致性。
- **优先级**：**P1**

### F3. R4、R5 与核心 steering 缺少发布层级和业务分类

- **定位锚点**：`requirements.md` → `## 2. 成功状态（§0.16 · 来源标注）`
- **问题**：成功状态只描述“本轮内沟通且不杀 SUB”，但 AC4、AC5 又把取消告知和配置文案纳入同一验收包。R4 有明确稳定性价值；R5 只给出禁用词，没有说明误解当前文案会造成什么真实操作损失。
- **问题根因**：把同一用户反馈附近发现的功能都合并成单一发布边界，没有区分核心刚需、稳定性保护和低风险 UX 澄清。
- **业务影响**：非核心文案可能阻塞 steering；也可能为了赶核心功能而弱化真正高风险的取消确认。
- **架构影响**：投递、破坏性操作、配置治理三个领域的交付和回滚边界不清。
- **修改建议**：
  - R1–R3：**A 业务刚需**，核心发布；
  - R4：**B 稳定性保护**，可独立交付但必须先解决 A2；
  - R5：补具体误操作场景与缺失影响；答不出则降为独立 UX 微改，不阻塞核心；
  - R6：停止。
- **优先级**：**P1**

## 三、三路径反向比较

| 路径 | 收益 | 成本 | 主要风险 | 结论 |
|---|---|---|---|---|
| 沿用现有方案 | 无协议与一致性改造成本 | 用户只能等待或停止父轮 | 对话权缺失、误杀 SUB | 不可作为目标态，仅可作为不支持 agent 的降级 |
| 局部重构 | 默认排队、显式 Send Now、能力探测、队列可见性；改动相对可控 | 需补投递未知态、记录时序和安全取消语义 | 私有 steering 能力变化；无法提供远端 exactly-once | **推荐本轮路径**，但须先修 A1–A4，并拆出 R6 |
| 领域重构 | 后端统一投递聚合、持久 outbox、turn identity、幂等提交，可支持多窗口和恢复 | 成本高，且仅本端改造仍无法让 agent 去重 | 容易为尚未证明的离线、多窗口需求过度设计 | 本轮不做；只有确认需要可恢复投递，且上游愿意接收幂等键时再启动 |

## 四、保留、调整与停止

- **可保留**：默认排队、逐条「立即发送」、能力三态、队列可见、停止与发送并列、不在前端猜工具边界、`startedNewTurn` 禁止补发。
- **必须调整**：模糊传输失败语义、`startedNewTurn` 状态归属、会话记录排序、取消集合扩大时的再授权、Tasks 命令契约。
- **停止继续开发**：R6；A1 的投递契约确定前暂停 T2–T6；R4 的破坏性授权契约确定前暂停 T7。
- **独立降级处理**：R5 若无法证明真实误操作影响，不应阻塞核心 steering 上线。
