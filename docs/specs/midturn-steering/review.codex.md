# 第 1 轮评审结论

本轮仅依据 `requirements.md`、`design.md`、`tasks.md` 进行文档内部评审。

## 一、架构级问题

### A1. “等这步做完”由前端检测工具边界，无法保证需求语义

- **定位锚点**：`design.md` → `### 2.3 两种注入时机（R1.2）`
- **问题**：设计把待注入消息留在前端队列，由前端观察 tool-call 完成事件后再发 steering。但“工具结束”事件到达前端时，agent 可能已经开始下一步；页面刷新、断线、切换会话或多窗口也可能使观察者消失或重复执行。
- **问题根因**：把有顺序、一致性和恢复要求的调度职责放到了非权威、非持久的 UI 层。
- **业务影响**：消息可能晚一个边界、退化到轮末、刷新后遗失，无法兑现“当前工具结束、下一步开始前插入”。
- **架构影响**：前端成为第二个 turn 调度器，与后端连接状态形成双真源；后续难以处理重连、多窗口和响应乱序。
- **修改建议**：将 `mode/deliver_at` 作为明确命令意图传入拥有 turn/tool 生命周期的后端编排层，由同一状态机原子判定边界并投递；前端只负责选择时机和展示状态。若底层确实无法观察“下一步开始前”的可靠边界，应收缩需求语义，而不是声称安全退化即满足需求。
- **优先级**：**P0**

### A2. `startedNewTurn` 降级方案会重复发送同一用户消息

- **定位锚点**：`design.md` → `### 2.4 startedNewTurn 竞态处理`
- **问题**：`startedNewTurn` 已表示 steering 请求启动了一个包含该消息的新 turn，随后再走普通 prompt 会把同一消息发送第二次；还可能撞上刚启动的新 turn，触发忙碌拒绝。
- **问题根因**：缺少“检查 turn 状态—选择发送通路—提交消息”的原子决策，也没有统一的消息身份和幂等语义。
- **业务影响**：用户指令可能执行两次，例如重复派发、重复修改或重复调用外部工具。“宁可多发一轮”不是安全降级。
- **架构影响**：真实 agent turn 与本地 `turn_in_flight` 状态脱节；补发又扩大状态分叉。
- **修改建议**：禁止把已被上游接受的消息再次发送。优先在后端原子判定 busy/idle：busy 才调用 steering，idle 直接走普通 prompt；仍可能返回 `startedNewTurn` 时，应将其视为已接受并设计可观测/重同步策略，或明确该能力在此竞态下不可安全使用。所有重试需绑定稳定 message id。
- **优先级**：**P0**

### A3. 缺少最小投递领域模型，无法证明不丢、不重、可恢复

- **定位锚点**：`design.md` → `### 2.5 降级矩阵（R2.2 / R2.3 / C4）`
- **问题**：文档只列 `injected / failed / startedNewTurn` 分支，没有定义一条用户消息在排队、等待边界、发送中、已接受、已记录、回落之间的状态和合法迁移。
- **问题根因**：以命令分支和布尔能力标志代替投递聚合/状态机。
- **业务影响**：超时、重连、重复点击、响应丢失时无法判断该重试、等待还是已经成功，容易丢消息或重复执行。
- **架构影响**：队列、连接、会话记录、UI 各自维护局部状态，形成贫血且分散的流程模型。
- **修改建议**：补充轻量投递状态模型，不必引入复杂框架；至少定义 message id、connection/session/turn 归属、requested mode、状态迁移、终态、重试和去重规则，并指定唯一权威层。
- **优先级**：**P1**

### A4. 能力标志到前端的契约仍是悬空链路

- **定位锚点**：`design.md` → `## 7. 链路表与消费验证锚（§0.16）`
- **问题**：只写“session state → 前端发送键”，没有说明通过何种 DTO/API/事件传输、初始值是什么、重连或 agent 切换时如何更新。
- **问题根因**：设计证明了能力探测来源，却没有完成其消费者契约。
- **业务影响**：UI 可能长期按默认 false 展示，或在切换连接后沿用旧能力，导致错误发送预期。
- **架构影响**：核心能力接线仍可能成为“后端字段已建但生产消费者未接”的死链。
- **修改建议**：在链路表中补全权威字段、wire 字段、传输入口、刷新时机、默认/未知状态和真实消费者；是否已有可复用 session DTO **需实现方核实**。
- **优先级**：**P1**

### A5. 取消确认使用前端快照，取消范围与显示数量未形成一致契约

- **定位锚点**：`design.md` → `## 4. R4 破坏性告知设计`
- **问题**：读取 `active_delegations` 后再单独执行取消存在时间差；文档也未定义数量是当前会话、父 turn、连接还是全局范围，以及是否只统计实际可被本次取消级联终止的委托。
- **问题根因**：展示数据与破坏性操作没有共享同一权威范围定义。
- **业务影响**：确认框显示 3 个，实际可能取消 2 个或更多；多会话场景下可能误导用户。
- **架构影响**：取消语义散落于前端快照和后端级联实现，难以保持一致。
- **修改建议**：明确“可被本次取消影响的 delegation 集合”及其作用域；由后端权威计算取消影响，取消执行时再次校验。是否已有按 parent turn 精确过滤的快照 **需实现方核实**。
- **优先级**：**P1**

## 二、普通功能与需求问题

### F1. R1 的无条件“必须当前轮投递”与 R2 降级要求矛盾

- **定位锚点**：`requirements.md` → `### R1 mid-turn 注入（核心）`
- **问题**：R1.1 对所有场景要求当前轮投递，R2.2 又允许不支持 steering 的 agent 排队至轮末。
- **问题根因**：核心目标没有按“支持能力”和“不支持能力”划分适用条件。
- **业务影响**：同一不支持 agent 的行为会同时被判定为符合 R2、违反 R1。
- **架构影响**：测试和实现无法建立唯一验收基线。
- **修改建议**：明确 R1.1 的前置条件；把支持、未知、不支持及运行阶段暂不可注入分别定义为可测试行为。
- **优先级**：**P1**

### F2. R1.5 被推迟成实现阶段“确认，若缺再补”，关键数据契约未决

- **定位锚点**：`design.md` → `注入后的用户消息 | agent streaming input（已有） | 会话记录 + UI（**待验 R1.5**）`
- **问题**：会话记录可见性是明确需求，但设计没有决定由客户端预写、agent 事件回传还是后端确认后落库；任务仅写“若缺：补广播/落库”。
- **问题根因**：把关键持久化和展示责任延迟给执行者临场决定。
- **业务影响**：可能出现消息已影响 agent、但刷新后记录消失；也可能本地预写后因注入失败产生幽灵消息。
- **架构影响**：会话历史缺少单一真源，失败与重试语义不确定。
- **修改建议**：在设计阶段明确记录责任方、写入时机、失败状态、去重键及 UI 如何区分待发送/已接受/失败；不能留作 T6 探索性补丁。
- **优先级**：**P1**

### F3. AC1 依赖“≥60 秒”时间假设，验收不稳定且缺少消息关联

- **定位锚点**：`requirements.md` → `**AC1**：派发一个耗时 ≥60s 的子智能体后发消息`
- **问题**：耗时阈值不能保证验收时委托仍在运行，也没有规定如何证明回应对应本次注入而非先前上下文。
- **问题根因**：用时间近似替代可控同步条件和关联标识。
- **业务影响**：测试可能偶发失败或假通过。
- **架构影响**：无法形成稳定的端到端回归门。
- **修改建议**：使用可控阻塞/释放的测试委托或可观测 barrier；记录 delegation id、message id、turn id，并明确“回应发生于哪个 turn、检查状态发生于何时”。
- **优先级**：**P1**

### F4. AC2 的“即时注入”与默认“等这步做完”不一致

- **定位锚点**：`requirements.md` → `**AC2**：对一个不支持注入的 agent 发消息`
- **问题**：AC2 要求支持 agent 时“消息即时注入”，但 R1.3 明确默认等待工具边界，二者对默认操作的验收不同。
- **问题根因**：能力验收、时机选择验收和默认行为验收混写。
- **业务影响**：测试人员可能把正确的边界等待误判为失败，或把所有消息都按立即打断实现。
- **架构影响**：模式参数是否真正贯穿链路无法被准确验证。
- **修改建议**：分别验收支持能力下的默认边界模式、显式立即模式，以及不支持能力下的轮末排队模式。
- **优先级**：**P1**

### F5. R6 是典型 Solution-Jumping，缺少真实业务依据

- **定位锚点**：`requirements.md` → `### R6 resume 用户入口`
- **问题**：需求表述为“判定前端是否缺入口；若缺则补”，其依据只是技术能力存在、UI 可能缺失，没有说明谁会在什么操作下手输 session id、缺失会造成何种业务损失、现有恢复入口是否已覆盖。
- **问题根因**：把“代码里可能没有入口”直接转换成产品需求。
- **业务影响**：可能增加无人使用且容易误操作的 UI，扩大本次核心功能范围。
- **架构影响**：把独立的会话恢复领域混入 mid-turn 投递与委托治理，削弱边界和交付聚焦。
- **修改建议**：先补真实角色、场景、缺失影响、现有覆盖调查和业务分类；当前证据下应归 **D 技术缺口/技术洁癖**，建议移出本 spec。若能证明真实恢复损失，再作为独立需求定义，不使用“若缺则做”的条件式验收。
- **优先级**：**P1**

## 三、P2 补充意见

### P2-1. T0 是既成交付缺陷，与当前 spec 主线混杂

`tasks.md` 将已经提交的 enum 修复和补审放入当前功能任务，且没有对应需求或 AC。建议迁回独立缺陷工件；本 spec 只保留确有前置约束的引用，避免完成度、依赖图和审查范围失真。

### P2-2. R5 缺少可验证的用户理解标准

“用户读完能明白”不可稳定测试。建议用具体界面信息架构或用户操作结果验收，而不只做禁词匹配。同时补充其业务分类；当前更接近低风险 UX 澄清，不应与核心投递链路共同阻塞上线。
